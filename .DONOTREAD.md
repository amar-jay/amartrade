# Trade Map library implementation plan

This plan covers the Go library behind `amartrade`. The first milestone is a
reliable, agent-friendly client for the public Trade Map data API documented in
[`docs/trademap-api.md`](docs/trademap-api.md). Cobra commands are consumers of
the library, not part of it.

## Design rules

- [ ] Keep HTTP, validation, pagination, and provider models in
  `internal/trademap`; keep Cobra and output formatting in `cmd`.
- [ ] Accept `context.Context` on every operation that may perform I/O.
- [ ] Inject `*http.Client`; do not use package-level mutable clients or state.
- [ ] Represent every provider code as a string so values such as `000`, HS
  codes, and EBOPS codes cannot lose leading zeroes.
- [ ] Model individual economies, economy groups, products, product groups,
  services, and periods as distinct types instead of interchangeable strings.
- [ ] Validate impossible selector combinations before making a request.
- [ ] Preserve provider values and codes in responses. Label resolution and
  derived calculations must be explicit, separate operations.
- [ ] Return errors; never print, log, or call `os.Exit` from the library.
- [ ] Never accept, persist, or expose browser tokens, cookies, or personal
  account data in this public-data client.

## Proposed package shape

```text
internal/trademap/
├── client.go            Client construction and shared request execution
├── errors.go            Typed transport, HTTP, decoding, and validation errors
├── codes.go             Economy, group, HS, EBOPS, period, and frequency types
├── selectors.go         Reporter, partner, and product/service selectors
├── reference.go         Reference-data client methods and catalogs
├── goods_timeseries.go  Goods time-series requests and responses
├── services_timeseries.go
├── indicators.go        Trade indicators and availability
├── coverage.go          Coverage queries
├── companies.go         Optional public company search
├── pagination.go        Explicit bounded page traversal
└── testdata/            Small sanitized response fixtures
```

Keep the package internal while its API is changing. Once two real consumers
use it without provider details leaking into their code, evaluate moving it to
a top-level public `trademap` package.

## Phase 1 — Core contracts and transport

- [ ] Add `Client` with options for base URL, HTTP client, user agent, and
  conservative defaults.
- [ ] Reject nil or unusable configuration at construction time.
- [ ] Implement one shared JSON request path with correct query encoding,
  response-size limits, content-type checks, and useful decode errors.
- [ ] Define typed errors that preserve HTTP status and a bounded provider
  message without retaining an entire response body.
- [ ] Implement a retry policy for transient network failures, `429`, and
  selected `5xx` responses; honor context cancellation and `Retry-After`.
- [ ] Do not retry validation errors or other `4xx` responses.
- [ ] Add configurable request pacing suitable for batch/agent workloads.
- [ ] Unit-test all transport behavior with `httptest.Server`.

**Done when:** a caller can construct a client, cancel a request, distinguish
validation/transport/HTTP/decode failures, and test without internet access.

## Phase 2 — Codes, selectors, and validation

- [ ] Define string-backed code types for economies, economy groups, HS
  products, product groups, EBOPS services, and indicator IDs.
- [ ] Define enums for flow, frequency, dimension, unit, output mode, and
  period granularity without allowing arbitrary wire values.
- [ ] Create reporter/partner selectors that encode either one economy or one
  economy group, never both.
- [ ] Create goods selectors that encode either an HS product or product group.
- [ ] Create service selectors with explicit support for aggregate service
  requests (`ALL`) and returned total code (`S00`).
- [ ] Add period constructors and validation for yearly, quarterly, and monthly
  formats.
- [ ] Verify all query serialization in table-driven tests, including `000`,
  group IDs, leading-zero codes, empty values, and reserved characters.

**Done when:** invalid combinations fail locally and every valid selector maps
to exactly one documented wire representation.

## Phase 3 — Reference data and resolution

- [ ] Implement reference calls for economies and economy groups.
- [ ] Preserve group membership and distinguish group IDs from member economy
  codes.
- [ ] Implement HS product, product-group, and EBOPS service catalogs.
- [ ] Add other classifications only when a data endpoint needs them.
- [ ] Build immutable lookup indexes by code and normalized label.
- [ ] Support exact code lookup, exact-name lookup, and deterministic ambiguous
  match errors; keep fuzzy search outside the core client initially.
- [ ] Add an optional in-memory TTL cache with request coalescing. Make cache
  bypass/refresh explicit.
- [ ] Defer persistent disk caching until reference payload size and change
  frequency have been measured.

**Done when:** callers can discover valid codes and resolve returned codes to
labels without hard-coded country or classification tables.

## Phase 4 — Goods time series

- [ ] Implement yearly, quarterly, and monthly requests.
- [ ] Support `byProduct`, `byCountry`, and `byPartner` through typed request
  structs or dimension-specific methods.
- [ ] Model `records`, `aggregateRecords`, pagination fields, reference year,
  and sources without discarding unknown response fields needed for diagnosis.
- [ ] Expose `Page` methods first, then a bounded iterator and an explicit
  `AllPages` helper with maximum-page/record limits.
- [ ] Keep units and scaling metadata alongside values.
- [ ] Add sanitized fixtures for each frequency and dimension, including an
  economy-group result.

**Done when:** all nine goods time-series route combinations can be queried and
paginated without callers assembling raw query strings.

## Phase 5 — Services time series

- [ ] Implement yearly and quarterly service requests.
- [ ] Support `byService`, `byCountry`, and `byPartner` dimensions.
- [ ] Reuse common pagination and economy selectors without forcing goods HS
  concepts into service requests.
- [ ] Test aggregate service behavior and the `ALL` request / `S00` response
  distinction.

**Done when:** all six service route combinations have fixtures and validation
coverage equivalent to goods time series.

## Phase 6 — Indicators and coverage

- [ ] Implement indicator-availability queries before indicator data queries.
- [ ] Validate requested indicators against availability when the caller asks
  for strict validation; allow an explicit raw/forward-compatible mode.
- [ ] Implement `byProduct`, `byCountry`, and `byPartner` indicator queries.
- [ ] Document indicator meanings from observed metadata rather than guessing
  semantics from IDs.
- [ ] Implement coverage endpoints and expose coverage as a preflight helper.
- [ ] Add fixtures for unavailable periods, empty results, and partial coverage.

**Done when:** callers can determine whether a query is supported and can tell
the difference between “no trade,” “not covered,” and “invalid request.”

## Phase 7 — Optional company data

- [ ] Keep company search in a separate file and API surface so aggregate trade
  use does not depend on it.
- [ ] Confirm its public fields, pagination, and classification filters.
- [ ] Explicitly omit or redact any returned access-token-like field.
- [ ] Add this phase only after the aggregate trade MVP is complete.

## Phase 8 — Agent-friendly consumer layer

- [ ] Define a stable CLI JSON envelope containing query metadata, records,
  aggregates, sources, pagination, and warnings.
- [ ] Offer JSON for complete structured output and JSON Lines for streamed
  multi-page output; add CSV only where records are naturally tabular.
- [ ] Keep data on stdout and diagnostics/debug details on stderr.
- [ ] Add `--resolve-labels` without replacing raw codes.
- [ ] Add explicit `--max-pages`, `--max-records`, `--timeout`, and cache flags.
- [ ] Map typed library errors to stable CLI exit codes and machine-readable
  error output.
- [ ] Implement reference-list commands before complex data commands so agents
  can discover valid inputs.

**Done when:** an agent can discover codes, issue a bounded query, resume or
paginate deterministically, and parse both success and failure without scraping
human-readable text.

## Phase 9 — Verification and maintenance

- [ ] Maintain offline unit and fixture tests as the default test suite.
- [ ] Add opt-in live contract tests guarded by an environment flag; make them
  read-only, low-volume, and non-blocking for releases.
- [ ] Add fuzz tests for period parsing, selectors, URL encoding, and response
  decoding.
- [ ] Run tests with the race detector for cache and pagination code.
- [ ] Detect schema drift by retaining representative fixtures and testing
  required fields while tolerating additive fields.
- [ ] Add redaction tests proving tokens, cookies, email addresses, and raw
  response bodies cannot enter logs or fixtures accidentally.
- [ ] Document rate-limit behavior, reproducible examples, and known upstream
  instability.

## MVP completion checklist

- [ ] Reference catalogs expose economies, economy groups, HS products/product
  groups, and EBOPS services.
- [ ] Goods and services time-series endpoints are fully represented.
- [ ] Both individual-economy and economy-group queries work.
- [ ] Pagination is explicit and bounded.
- [ ] Structured JSON output is stable and tested.
- [ ] All normal tests run offline and contain no secrets or personal data.
- [ ] The API guide and CLI help match the implemented behavior.

## Decisions to revisit after the MVP

- [ ] Promote `internal/trademap` to a public module only after its abstractions
  survive real CLI and agent use.
- [ ] Decide whether persistent reference-data caching is worth its invalidation
  and portability cost.
- [ ] Decide whether fuzzy name resolution belongs in the library or a higher
  agent-facing layer.
- [ ] Decide whether automatic pagination should ever be a default; the safer
  initial behavior is one page unless the caller opts into bounded traversal.
- [ ] Evaluate additional providers behind a provider-neutral domain layer only
  after the Trade Map implementation is complete; do not generalize early.
